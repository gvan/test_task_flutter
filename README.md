# 3

При зміні сортування виникала наступна проблема:
- маємо початкове сортування, на першій позиції показується товар X;
- змінюємо сортування, на першій позиції показується товар Y;
- при кліку на товар Y відкривається екран з товаром X.

Проблема була в тому, що віджетом для товару є StatefulWidget. Об'єкт товару, який передавався в колбек кліку, був збережений в стейті окремим полем і ініціалізувався в initState. При зміні сортування айтемів на першій позиції замість товару X опинявся товар Y. build() метод викликався, тому на першій позиції ми бачимо дані товару Y, але initState() метод не викликався, тому змінна _selectedItem не перевизначалась і зберігала в собі товар X. 

Виклик initState() не відбувався через те, що при виклику Widget.canUpadte() для старого і нового віжетів перевіряється тип і ключ на рівність. Оскільки тип віджету однаковий і ключ дорівнює null, то canUpdate повертає true і новий стейт для віжета на першій позиції не створюється.

Рішенням було визначити ключ для кожного товару використовуючи id товару. Можна передавати об'єкт widget.item в onPressed() замість _selecteItem, але збереження товару в стейті може бути зроблено для реалізації майбутньої логіки, наприклад, додавання коментара до товару з полем вводу всередині айтема списку.

Додав widget-тест на перевірку оновлення стейту елементів списку після сортування товарів test/features/items/screens/update_items_state_on_sort_test.dart.

# 6

Обрані товарии зберігаються у вигляді id в репозиторії. Оскільки необхідно динамічно оновлювати список обраних товарів при додаванні/видаленні з обраного, було реалізовано підписку на обрані товари через StreamController. Підписка на список обраних товарів використовується на екрані списку обраних товарів і на екрані деталей товару, щоб показуати стан кнопки обраного. StreamController не підтримує збереження і відправку поточного стану для нових підписок, тому в репозиторії після створення стріму треба викликати завантаження обраних товарів, що додасть обрані товари в стрім. Завантаження обраних товарів при кожній підписці емулює роботу з реальним сервером, де обрані можуть змінитись під час поточної сесії, нарпиклад, якщо користувач змінив обрані з іншого пристрою.

# 7

Пошук та фільтрація реалізовані всередині репозиторію, а не всередині провайдера, як було реалізовано з сортуванням. Сортування також перенесено в репозиторій. Реалізацію виконано в репозиторії, оскільки при роботі з реальним сервером фільрацію, сорутвання і пошук треба робити через запит на сервер для того, щоб отримати вибірку по всім даним, а не тільки завантаженим локально. 

Отримання даних в провайдері від репозиторія реалізовано через підписку на стрім Future, а не напряму з Future. Це зроблено для того, щоб можна було відмінити підписку на запит, якщо під час його виконання прийшов новий запит. Таким чином, буде отримано дані тільки на останній запит. Ситуацію з частими запитами можна відтворити, якщо , наприклад, одрати категорію і дразу натиснути кнопку Скинути параметри. У пошуці для уникнення частої відправки запитів  додано debounce при вводі 500мс.

# Тестування

Додано окремий інтерфейс IItemsDataSource в ItemsRepository для того, щоб можна було мокати тестові дані в репозиторій без повторної реалізації функціоналу репозиторія. Додані юніт тести і тести інтерфейсу. Юніт тести тестують функціонал репозиторію, оскільки там лежить основна бізенс логіка. Тести інтерфейсу тестують вибір товару після сортування, віджет рейтингу, сортування, фільтрацію, пошук, скидання параметрів та обрані товари.
