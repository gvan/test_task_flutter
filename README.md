### 3

При зміні сортування виникала наступна проблема:
- маємо початкове сортування, на першій позиції показується товар X;
- змінюємо сортування, на першій позиції показується товар Y;
- при кліку на товар Y відкривається екран з товаром X.

Проблема була в тому, що віджетом для товару є StatefulWidget. Об'єкт товару, який передавався в колбек кліку, був збережений в стейті окремим полем і ініціалізувався в initState(). При зміні сортування айтемів на першій позиції замість товару X опинявся товар Y. Метод build() викликався, тому на першій позиції ми бачимо дані товару Y, але метод initState() не викликався, тому змінна _selectedItem не перевизначалась і зберігала в собі товар X. 

Виклик initState() не відбувався через те, що при виклику Widget.canUpdate() для старого і нового віджетів перевіряється тип і ключ віджета на рівність. Оскільки тип віджету однаковий і ключ дорівнює null, то canUpdate повертає true і новий стейт для віджета на першій позиції не створюється.

Рішенням було визначити ключ для кожного товару використовуючи id товару. Можна передавати об'єкт widget.item в onPressed() замість _selectedItem, але збереження товару в стейті може бути зроблено для реалізації майбутньої логіки, наприклад, додавання коментаря до товару з полем вводу всередині айтема списку.

Додав widget-тест на перевірку оновлення стейту елементів списку після сортування товарів test/features/items/screens/update_items_state_on_sorting_test.dart.

### 4

Змінено розміщення та стилі елементів екрану детальної інформації товару. Для великих екранів і горизонтального положення елементи розділені на два блоки по горизонталі. Картка з іконкою в блоці ліворуч і детальна інформація в блоці праворуч.

### 5

Додано анімацію при натисканні на картку з іконкою для зміни стану. В необраному стані картка показує іконку кольору товару і напівпрозорий фон. В обраному стані картка показує білу іконку і фон кольору товару. Додано обробку повторних натискань до завершення анімації зміни стану.

### 6

Обрані товари зберігаються у вигляді списку id в репозиторії. Оскільки необхідно динамічно оновлювати список обраних товарів при додаванні/видаленні з обраного, було стрім обраних товарів через StreamController. Підписка на список обраних товарів виконується на екрані списку обраних товарів і на екрані деталей товару, щоб показувати стан кнопки обраного. StreamController не підтримує збереження і відправку поточного стану для нових підписок, тому в репозиторії після створення стріму треба викликати завантаження обраних товарів, що додасть обрані товари в стрім. Завантаження обраних товарів при кожній підписці емулює роботу з реальним сервером, де обрані можуть змінитись під час поточної сесії, наприклад, якщо користувач змінив обрані з іншого пристрою.

### 7

Пошук та фільтрація реалізовані всередині репозиторію, а не всередині провайдера, як було реалізовано з сортуванням. Сортування також перенесено в репозиторій. Реалізацію виконано в репозиторії, оскільки при роботі з реальним сервером фільтрацію, сортування і пошук треба робити через запит на сервер для того, щоб отримати вибірку по всім даним, а не тільки завантаженим локально. 

Отримання даних в провайдері від репозиторія реалізовано через підписку на стрім від Future, а не напряму з Future. Це зроблено для того, щоб можна було відмінити підписку на запит, якщо під час його виконання прийшов новий запит. Таким чином, буде отримано дані тільки на останній запит. Ситуацію з частими запитами можна відтворити, якщо, наприклад, обрати категорію і одразу натиснути кнопку Скинути параметри. Очікування на виконання запиту при виклику методу завантаження реалізовано через Completer, це необхідно для очікування завантаження через PullToRefresh.

У пошуці для уникнення частої відправки запитів додано debounce при вводі 500мс.

### Тестування

Додано окремий інтерфейс IItemsDataSource в ItemsRepository для того, щоб можна було мокати тестові дані в репозиторій без повторної реалізації функціоналу репозиторія. Додані юніт тести і тести інтерфейсу. Юніт тести тестують функціонал репозиторію, оскільки там лежить основна бізенс-логіка. Тести інтерфейсу тестують вибір товару після сортування, віджет рейтингу, сортування, фільтрацію, пошук, скидання параметрів та обрані товари.
